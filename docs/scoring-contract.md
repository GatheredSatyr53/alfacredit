# Контракт с сервисом скоринга

Сервис скоринга (Python, отдельный контейнер `scoring` в docker compose) **заменяет расчёт на этапе Scoring**.
Он возвращает оценку риска и объяснение, а кредитное решение остаётся в backend на C#: стоп-факторы,
лимиты продукта, политика по грейдам (`docs/decision-logic.md`). Если сервис недоступен, backend
использует встроенную балльную модель и помечает результат `RulesFallback`, чтобы демо никогда не блокировалось.

В репозитории лежит **заглушка** сервиса по этому контракту (`scoring/`, стандартная библиотека Python, без зависимостей):
с ней стенд поднимается одной командой, а интеграция проверена end-to-end. Сервис ML-команды заменяет её,
сохранив адрес, порт, `GET /health` и формат `POST /api/v1/score`; backend менять не нужно.

## Как backend вызывает сервис

| Что | Значение |
|---|---|
| Адрес | `POST http://scoring:8000/api/v1/score` (имя сервиса в compose `scoring`, порт `8000`; настройка `Scoring__BaseUrl`) |
| Health | `GET http://scoring:8000/health` отвечает 200 и `{"status":"ok","model_version":"..."}`; backend показывает его в `/health/ready` как проверку `scoring` |
| Формат | JSON, UTF-8, поля в `snake_case`, `Content-Type: application/json`, тело с `Content-Length` |
| Таймаут и повторы | 5 секунд на запрос (`Scoring__TimeoutSeconds`), затем 2 повтора (`Scoring__Retries`) с паузами 1 и 2 секунды (`Scoring__RetryDelayMs` × номер попытки) |
| Ошибки | `400` с описанием, если payload невалиден: backend не повторяет запрос и сразу считает встроенной моделью. `5xx`, таймаут, обрыв связи: повторы, затем встроенная модель |
| Откат | результат помечается `source = RulesFallback`, `model_version = rules-v1`, в `warnings` добавляется `external_scoring_unavailable`; заявка идёт дальше и не зависает |
| Идемпотентность | `request_id` уникален для каждого расчёта; повтор с тем же `request_id` можно обслужить из кэша |

Сервис не принимает решений и не читает базу: всё, что ему нужно, приходит в запросе.

## Правила для данных

- **Единицы**: деньги в рублях, целыми числами без форматирования (`1500000`, не `"1 500 000"` и не тысячи); backend округляет до рубля.
  Годовые показатели за последние 12 месяцев, месячные за календарный месяц; период всегда в названии поля.
  Ставка в процентах годовых дробным числом (`19.5`).
- **Пропуски**: поле присутствует со значением `null`. `NaN` и `Infinity` в JSON недопустимы и не будут отправляться.
  Если внешняя проверка не получена целиком, `null` стоит на месте всего блока (`"credit_bureau": null`).
- **Что не передаётся**: дата, к которой клиенту нужны деньги (`needByDate` заявки, `docs/financing-preview.md`),
  в запрос не входит: это план клиента, а не фактор риска. Предварительный подбор сервис скоринга не вызывает.
- **Неизвестные поля**: сервис игнорирует поля, которых нет в контракте (например, `checks.egrul.registered_at` и `okved`
  backend передаёт как есть из симулятора); backend так же игнорирует лишние поля ответа.
- **Даты**: ISO 8601, даты без времени `2019-03-12`, метки времени в UTC `2026-10-20T13:17:20Z`.
- **Перечисления**: строки как в API backend (см. `docs/api.md`): `legal_form` = `Ooo | Ip`,
  `tax_regime` = `Osno | UsnIncome | UsnIncomeExpenses | Patent`,
  `product_type` = `WorkingCapital | Investment | Overdraft | CreditLine | Express`,
  `purpose` = `WorkingCapital | Equipment | Expansion | Refinancing | Other`.
- **Оценка**: `score` целое 0..100, чем выше, тем ниже риск; `risk_grade` буква A..E по шкале ниже.
  Backend использует грейд, `score` нужен для сортировки очереди и графиков.

| Грейд | score | Что делает backend |
|---|---|---|
| A | 80..100 | автоодобрение на запрошенных условиях, если сумма в лимите продукта |
| B | 65..79 | автоодобрение, ставка +1.5 п.п. |
| C | 50..64 | одобрение с изменёнными условиями: сумма до 25 % годовой выручки, ставка +3 п.п. |
| D | 35..49 | ручное рассмотрение менеджером |
| E | 0..34 | отказ |

Сервис может вернуть грейд, не совпадающий с таблицей по `score`, если модель так считает; backend доверяет грейду.
Если грейд не распознан (не A..E), backend выводит его из `score` по таблице. Стоп-факторы и лимит автоодобрения
backend проверяет отдельно, до применения грейда.

| Поле | Тип | Описание |
|---|---|---|
| `request_id` | uuid строкой | уникален для каждого расчёта; backend хранит его вместе с результатом, по нему расчёт ищется в логах сервиса |
| `application.amount_rub`, `term_months`, `purpose` | int, int, enum | что просит клиент |
| `application.estimated_monthly_payment_rub` | int | аннуитетный платёж по базовой ставке продукта, считает backend (`LoanMath.MonthlyPayment`) |
| `application.product.*` | | параметры продукта: тип, базовая ставка, залог, лимит автоодобрения |
| `application.collateral_offered` | bool | предложил ли клиент залог (пока всегда `false`) |
| `company.region_code` | string | первые две цифры ИНН |
| `company.business_age_months` | int | полных месяцев с даты регистрации |
| `company.financials.*` | int или null | выручка, расходы, чистая прибыль за 12 месяцев, текущие платежи по кредитам в месяц |
| `company.history.*` | int | заявки, отказы и выданные кредиты этого клиента в нашей системе |
| `checks.egrul.status` | enum | `Active`, `Liquidating`, `Terminated` |
| `checks.fns.*` | | налоговая задолженность, блокировка счетов, выручка по отчётности ФНС (может быть `null`) |
| `checks.credit_bureau.*` | | кредитная история: обязательства, платежи, просрочки за 24 месяца, списания |
| `checks.fssp.*` | | открытые исполнительные производства и их сумма |

Любой блок в `checks` может быть `null`, если источник не ответил. Backend тогда помечает заявку
«проверка недоступна», но скоринг всё равно запрашивает.

## Ответ

```json
{
  "request_id": "01a15975-f14b-7636-a356-687331e9eb8d",
  "model_version": "lgbm-2026.10.21",
  "score": 78,
  "risk_grade": "B",
  "probability_of_default": 0.06,
  "factors": [
    {
      "code": "debt_load",
      "title": "Долговая нагрузка",
      "impact": -8,
      "value": "0.48",
      "client_explanation": "Платежи по кредитам занимают около половины месячной прибыли."
    },
    {
      "code": "business_age",
      "title": "Возраст бизнеса",
      "impact": 10,
      "value": "7 лет 7 мес.",
      "client_explanation": "Компания работает больше трёх лет."
    },
    {
      "code": "credit_history",
      "title": "Кредитная история",
      "impact": 15,
      "value": "без просрочек",
      "client_explanation": "Просрочек по кредитам за два года нет."
    }
  ],
  "warnings": [],
  "missing_data": []
}
```

| Поле | Тип | Описание |
|---|---|---|
| `request_id` | string | эхо запроса, для сопоставления в логах |
| `score` | int 0..100 | обязательно |
| `risk_grade` | `A`..`E` | обязательно |
| `probability_of_default` | float 0..1 или null | желательно, показывается менеджеру |
| `factors` | массив | 3..7 главных факторов по убыванию модуля `impact`; `impact` в баллах со знаком, `value` строка для карточки, `client_explanation` фраза для клиента простым языком; `title` и `client_explanation` на русском. `code` в snake_case без префикса `factor_` (например `debt_load`): в причинах решения backend сам добавляет `factor_`, а уже имеющийся префикс не удваивает |
| `warnings` | массив строк | предупреждения модели: чем заменены отсутствующие входы (`net_profit_missing`), особенности расчёта |
| `missing_data` | массив строк | каких входов не хватало: пути полей запроса, например `checks.credit_bureau`, `company.financials.net_profit_rub`. Backend дополняет список тем, что сам отправил как `null` |
| `model_version` | string | сохраняется в заявке для воспроизводимости |

Backend разбирает ответ терпимо: числа могут прийти строкой, дробный `score` округляется, неизвестный грейд выводится
из балла, отсутствующие `factors`, `warnings`, `missing_data` считаются пустыми. Нет только `score` или тело не JSON:
ответ считается ошибкой, применяется откат на встроенную модель.

Ответ с ошибкой валидации:

```json
{ "error": "validation", "details": { "company.financials.revenue_rub": "must be >= 0" } }
```

## Что backend сохраняет (`scoring_results`)

| Поле | Откуда |
|---|---|
| `request_id` | из запроса |
| `score`, `grade`, `probability_of_default` | из ответа |
| `factors` (jsonb), `warnings`, `missing_data` | из ответа; `missing_data` объединяется с пропусками, которые backend отправил как `null` |
| `model_version` | из ответа (`rules-v1` для встроенной модели) |
| `source` | `External`, `RulesFallback` или `Rules` |
| `duration_ms`, `computed_at` | длительность вызова с учётом повторов и момент расчёта |

Менеджер видит всё это в `GET /api/applications/{id}` (поле `scoring`), клиент видит только решение и его причины,
построенные на `client_explanation` факторов.

## Что нужно от сервиса для сдачи

- Dockerfile и сервис `scoring` в `docker-compose.yml` (уже есть, достаточно заменить содержимое `scoring/`), без платных API и закрытых моделей.
- `GET /health` для healthcheck, запуск без GPU на обычном ПК.
- Модель с открытыми весами, если используется LLM; классический ML без ограничений.
- Версии зависимостей зафиксированы (`requirements.txt` с версиями или lock-файл), базовый образ с точным тегом.
- Описание признаков и логики в `README` сервиса: жюри оценивает объяснимость.
